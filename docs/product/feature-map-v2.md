## 1. 这份功能表解决什么问题

QUTCraft Commons 已从“门户原型”进入多模块并行开发阶段。单纯按页面名称记录进度，容易把“界面存在”“接口存在”“完整闭环可用”混为一谈。本表将每项能力拆成三个层次：

1. **当前实现**：以仓库中的前端、Go 路由、OpenAPI 和测试为准。
2. **MVP 收口**：8 月 31 日前必须达到的可演示、可验收状态。
3. **扩展方向**：保留接口与数据模型空间，但不默认进入当前迭代。

公开门户仍是独立宣传官网，不是后台的只读镜像。管理端负责内容生产和组织协作；自定义门户只能使用公开 Portal API。

## 2. 标记与优先级

### 2.1 实现状态

| 标记 | 含义 | 判定标准 |
| --- | --- | --- |
| ✅ | 已形成基础闭环 | 页面与真实 API 已连接，主要成功路径可运行。 |
| 🟢 | MVP 基础能力可用 | 当前能力可用于比赛/封闭演示，但仍保留体验或运营增强项。 |
| 🟡 | 部分完成 | 页面、接口、契约或持久化中至少一层缺失。 |
| ⬜ | 未实现 | 只有需求描述，尚无可用入口。 |
| 📐 | 仅有契约/设计 | 已有规范、类型或原型，但运行时尚未实现。 |
| ➕ | 扩展项 | 不属于 `v0.1.0-mvp` 的发布阻断项。 |

状态表示“仓库当前事实”，不是对质量的永久承诺。功能只有符合本文第 9 节的完成定义，才能在发布检查中标为完成。

### 2.2 优先级

| 优先级 | 定义 | 调度规则 |
| --- | --- | --- |
| P0 | 发布阻断 | 平台核心闭环、AI 活动服务闭环或安全边界所必需；优先修复。 |
| P1 | MVP 增强 | 提升完整度与比赛表达；不能挤占未完成 P0。 |
| P2 | 版本扩展 | 进入 `v0.2+`，先保留 API/模型扩展点。 |

## 3. MVP 的四条核心闭环

```text
内容闭环：后台创建/编辑 → 发布 → Portal API → 门户展示 → 下线后消失

申请闭环：门户提交申请 → 后台审批 → 审计记录 → Mock/RCON Adapter → 明确结果

门户闭环：选择 Portal Manifest → 加载公开能力 → 主题呈现 → 失败时回退 MD3

AI 活动服务闭环：结构化活动需求 → 选择组织知识 → 生成带引用方案 → 人工批准 → 创建项目/里程碑/CMS 草稿 → 人工发布
```

8 月 31 日的比赛版必须优先保证这四条链路连续三次成功。成员、项目、知识库和资源能力用于支撑平台闭环与 AI 活动服务，而不是把后台扩展成通用 OA。

## 6. 扩展路线

扩展项按价值和依赖分层，不按“看起来酷”决定先后。

### v0.2：运营与协作增强

- 内容差异/导出和定时发布；复杂富文本仍不在近期范围。
- 成员档案、邀请模板多语言和成员筛选。
- 组织搜索与跨组织聚合；默认组织偏好已作为多组织体验收口完成。
- 项目任务看板、评论、附件和里程碑提醒。
- 知识库全文搜索、文章关联和导入/导出。
- 资源版本、下载报表、MinIO/S3 签名 URL。
- 申请审批通知的 Webhook/企业微信、多实例队列与退信处理。
- Portal 公开知识问答和只读组织运营周报。
- 多模型路由、复杂工具审批和智能体工作流编排。

进入条件：`v0.1.0-mvp` 的平台闭环与 AI 活动服务闭环稳定，权限与数据隔离测试通过，OpenAPI 不再频繁破坏性变更。

### v0.3：多组织与生态适配

- 多组织生命周期、租户级配额与跨组织运营聚合。
- 多服务器、多个 `ServerAdapter` 实例和统一状态聚合。
- 门户版本管理、灰度、回滚、自定义域名和可安装主题包。
- 组织级 Webhook、外部身份源和标准化数据导入。

进入条件：单组织部署完成真实使用验证；组织隔离、审计和配置模型经安全评审。

### v1.0：平台化能力

- 插件/适配器市场，但只接受声明式或受沙箱限制的扩展。
- 工作流编排、自定义表单、自定义角色和策略授权。
- 高可用部署、对象存储集群、异地备份和完整监控体系。
- 面向比赛与真实社团部署的版本治理、升级兼容和长期支持策略。

进入条件：扩展安全模型、版本兼容策略、运维责任和插件审核机制全部明确。不得以“执行任意第三方后端代码”作为捷径。

## 7. 依赖与开发顺序

| 能力 | 必须先稳定的依赖 | 原因 |
| --- | --- | --- |
| 内容/知识/资源公开 | 内容状态机、公开 DTO、缓存失效 | 防止草稿或内部字段泄露。 |
| 成员邀请 | 用户唯一性、成员关系、Token 生命周期、RBAC | 避免重复账户和越权加入。 |
| 项目成员/里程碑 UI | 项目权限、活跃成员列表、现有 CRUD API | 页面不能绕过服务端项目范围。 |
| 审批到服务器 | 申请持久化、审批事务、审计、ServerAdapter | 防止“批准成功但服务器未执行”的假成功。 |
| 自定义门户运行时 | Portal API 冻结、Manifest 校验、默认 MD3 回退 | 避免主题绑死内部接口或拖动核心契约。 |
| 通知 | 业务事件可靠持久化、密钥配置 | 通知失败不能导致业务状态回滚或密钥泄露。 |
| AI 智能体 | RBAC、内容状态机、知识可见性、审计、稳定 DTO | AI 的有效权限必须是用户权限、工具白名单、运行策略与人工确认的交集。 |

## 8. 取舍规则

1. P0 未通过阶段门时，不开始新的 P2 页面。
2. “接口已写”不等于完成；前端、服务端、契约、持久化和测试必须分别标记。
3. 外部依赖不可用时使用明确标识的适配器或降级状态，不伪造真实成功。
4. MVP 可减少编辑器、搜索、通知等体验增强，但不能削弱权限、审计、数据隔离和回退。
5. 新需求先归入本表的领域与版本；若会改变 P0 路径，必须同步调整 [schedule.md](../../schedule.md)。

## 9. 功能完成定义

一项功能只有同时满足以下条件，才可从 🟡/📐 改为 ✅：

- 用户入口和成功、空、失败、冲突/权限路径均有明确表现。
- OpenAPI、Go 实现和 TypeScript client 字段一致。
- 数据需要持久化时不依赖进程内临时状态或前端常量。
- 服务端执行真实授权，敏感字段不进入 Portal API。
- 至少有一条自动化测试，核心闭环另有 Compose 环境冒烟记录。
- README、功能表和相关规范已同步，不以 Mock 冒充生产能力。
